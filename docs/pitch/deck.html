04 / 12
Architecture

Nine on-chain contracts.
Each plays a specific, scoped role.

LoanRegistry
Central state ledger. Every loan's status, milestones, budget, and permitted recipients live here. All lifecycle transitions flow through this contract.
LoanVault
Custodian of loan USDC. Locks funds at disbursement. Releases to the agent's spending wallet only when a milestone is attested by the lender.
CreditRegistry
On-chain financial identity per agent address. Tracks repayment history, defaults, and calculates evolving credit limits. An agent's financial reputation lives here.
RevenueRouter
Accepts incoming USDC revenue from agent economic activity. Automatically splits it between lender repayment and the agent's operational share per loan terms.
LiquidityPool
Shared LP pool. Depositors earn yield across multiple funded agent loans. Reconciles performance as repayments arrive or defaults occur.
CollateralVault
Holds agent-posted USDC collateral. Transfers to the lender on default. Enforces LTV caps at loan origination.
UnderwriterPool
Third parties stake USDC to back specific agents. Stake is reserved when a loan is created and seized in partial shortfall recovery after default.
ReservePool
Protocol-level reserve. Funded by authorized contributors. Pays remaining lender shortfall after collateral and underwriter recovery are exhausted.
RecipientRegistry
Admin-curated whitelist of approved vendor addresses with category tags. Loan funds can only flow to registry-approved addresses declared in the proposal.

All contracts: UUPS upgradeable, Solidity 0.8.24, OpenZeppelin. Single-command Foundry deploy script for Arc Testnet.

Programmable Credit

Credit controlled by code,
not by human discretion.

📏
Evolving credit limits
CreditRegistry tracks each agent's repayment history, including successful and early repayments and defaults. Demonstrated repayment behavior can strengthen an agent's credit profile and increase its future credit limit.
🏔️
Milestone-gated disbursement
Loan proceeds are locked in LoanVault and released in defined stages. Each stage requires an on-chain attestation. Funds cannot be extracted in a single pull.
📋
Budget categories and recipient controls
Each loan declares a budget by category and a list of permitted recipient addresses. Recipients must be pre-approved in RecipientRegistry; creditWallet must appear in the declared list.
⛓️
Outstanding principal tracking
LoanRegistry tracks each agent's total outstanding debt across concurrent loans. New loans are blocked if they would exceed the agent's available credit.
🛡️
Layered recovery on default
Default triggers a defined on-chain sequence: vault recovery, collateral seizure, underwriter stake, reserve pool payout. Each layer is auditable and tamper-evident.
💧
Revenue-linked repayment
Agents route economic revenue through RevenueRouter. The contract splits incoming USDC between debt service and the agent's operational share according to the loan's repayment rate.
🔑
Keeper-authorized defaults
markDefault requires an authorized keeper address set by the protocol owner. Prevents permissionless griefing or premature default by third parties.
🔩
Lifecycle-gated configuration
Critical setters are guarded by loan-existence checks. Protocol contracts can only be rewired before any loans exist, preventing mid-flight configuration changes.

Agent Economy Use Cases

Any agent that generates revenue
can access Valen credit.

The examples below are illustrative use cases based on the protocol's design. Valen is in prototype stage on testnet. No production agents are currently operating on the platform.

🛒 Commerce Agent
Manages procurement: purchasing materials and paying suppliers. Borrows to fund an order, delivers goods, collects payment, and routes revenue through RevenueRouter for debt servicing. Budget categories constrain which vendors it can pay.
🔬 Research and Data Agent
Purchases compute, data feeds, and API access per project. Borrows per engagement, delivers analysis, invoices the client through RevenueRouter, repays from client payment.
✈️ Travel and Logistics Agent
Books travel, accommodation, and services on behalf of a user. Fronts costs via credit, completes booking, receives repayment from the user's subscription or reimbursement.
⚙️ Digital Services Agent
Provides content creation, translation, or technical services. Funded upfront by Valen credit. Revenue from service delivery flows back through RevenueRouter to the lender.
🤝 Agent-to-Agent Economy
One agent commissions another to complete a subtask. Valen credit enables agents to act as buyers simultaneously with being sellers, without requiring human capital backing for every transaction.
Integration model
Developer → their agent → Valen API/SDK → credit infrastructure

Valen does not build or host agents. It provides the financial layer that developer-built agents run on. Valen's role is infrastructure, not agent runtime.

Why Valen

Credit infrastructure built for
machine borrowers.

🤖
Designed around agent identity, not human identity
CreditRegistry builds a loan history per agent address. Credit limits grow with demonstrated repayment. An agent earns its own financial track record independent of its developer's identity.
⚙️
Fully on-chain loan lifecycle
Every state transition (request, approval, funding, milestone release, repayment, default) is an on-chain transaction with an emitted event. No off-chain database owns the authoritative loan state.
🔗
Revenue-linked repayment primitive
RevenueRouter connects revenue inflows directly to debt reduction. When revenue is routed through the protocol, it is split and applied to debt service automatically. Lenders receive on-chain USDC settlement, not off-chain promises.
🛡️
Layered risk infrastructure
Three independent recovery layers (collateral, underwriter staking, reserve pool) provide configurable risk calibration per loan type and per agent credit history depth.
💵
USDC-native on Arc
Built on Arc where USDC is the native gas token. All lending, repayment, and settlement use USDC. No cross-token conversion in the core flow. Stable, predictable transaction costs.
🔌
Developer integration surface is already defined
ABIs, event listeners, transaction scripts, and contract config are already in the codebase. The integration surface for developers connecting their agents is designed, not hypothetical.

Product Today

A working testnet protocol.
The core on-chain loan lifecycle runs end-to-end on Arc Testnet.

Demonstrable on testnet today

1. Register an approved recipient
Admin approves a vendor address in RecipientRegistry with a category tag. Controls where loan funds can ultimately flow.
2. Submit a loan proposal
Define principal, duration, milestones, budget categories, and permitted recipients. Validated against CreditRegistry and RecipientRegistry on-chain at request time.
3. Fund and activate
A lender or the LiquidityPool funds the loan. USDC is locked in LoanVault. Loan transitions to Active status.
4. Release milestones and route revenue
Lender attests milestones. Revenue flows through RevenueRouter to service the debt. Repayment tracked and credit history updated on-chain.
5. Default and recovery (if needed)
An authorized keeper marks default. Vault, collateral, underwriter, and reserve recovery layers execute in sequence. Pool reconciliation tracks every USDC.

Security and Risk Model

Financial infrastructure requires
serious security discipline.

Internal security audit: 19 findings reviewed

1 Critical resolved: vault fund lock after default (RISK-01)
6 High resolved: permissionless calls, pool accounting, test coverage (RISK-02–07)
6 Medium resolved: credit limits, reconciliation, one-way setters (RISK-08–13)
1 Accepted operational risk: owner key management (RISK-06)
4 Low / informational open: deploy script gap, timelocks, event gaps (RISK-16–19)
1 Accepted design characteristic: underwriter commitment semantics (RISK-14)
RISK-15 resolved: recipient cross-validation, creditWallet must be registry-approved and in permittedRecipients

This is an internal security review, not an independent third-party audit. The protocol is on testnet. It has not been independently audited or deployed to mainnet with real funds. An independent audit is a prerequisite before any mainnet deployment.

Security mechanisms in the protocol

🔑
Keeper-gated defaults
markDefault requires an authorized keeper, not callable by arbitrary addresses. Prevents griefing, premature default, and credit score manipulation.
📋
Recipient allowlisting
RecipientRegistry ensures loan funds can only flow to admin-approved addresses. The creditWallet must be registry-approved and explicitly declared in the proposal's permitted recipient list.
📐
Lifecycle-gated configuration
Protocol contract addresses can only be reconfigured before any loans exist. Prevents mid-flight rewiring attacks.
🔁
Layered default recovery
On-chain recovery sequence (vault, collateral, underwriter, reserve) with per-loan accounting guards to prevent double-counting or overpayment to the reserve.
